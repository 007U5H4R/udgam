# Stage 10 security review — area `m2-infra`

- **Branch / commit:** `build/stage7` @ `dd7b0c136453d17bbdc45680edc3dac8e0437991` (dd7b0c1)
- **Reviewer scope:** (1) `(buyer)` and `(processor)` route groups, their Server Actions, `src/lib/{agreements,processing,custody,batches,attestations}` and settlement; (2) `src/lib/ledger/evm`, the viem clients, `contracts/` (Solidity), deploy and anchor scripts, private-key handling; (3) `src/lib/db` (raw `sql`, triggers, migrations), `scripts/`, `.github/workflows`, `next.config.ts`, `.gitignore`, runtime dependencies.

## Method
1. Read-only clone at the commit (`<scratchpad>/s10-m2-infra`); `pnpm install --frozen-lockfile` for tests and probes only.
2. Code-path review of every Server Action under `(buyer)` and `(processor)` plus the admin settle action, the guards (`src/app/_auth/require.ts`, `src/lib/auth/{guards,session,org-scope}.ts`), every org-scoped read/write in `src/lib/{agreements,processing,custody,batches,attestations}`, the three contracts, the viem escrow/registry clients, deploy and key routines, migrations 0026–0034, both workflows, `next.config.ts`, `.gitignore`, `pnpm-workspace.yaml`.
3. Ran the existing cross-org and privacy tests as evidence for the clean items: `(buyer)/agreements/actions.int.test.ts`, `(processor)/actions.int.test.ts`, `processing/actions.int.test.ts`, `agreements/terms-private.int.test.ts` (18/18 green) and `tests/guard-coverage.test.ts` (9/9 green).
4. Probes (scratchpad `probes/`): concurrent operator transactions through the app's own `createEscrowChain` on a local Anvil (port 4540), and a raw viem control (port 4541). `pnpm audit --prod`. `git check-ignore -v` on key-file paths.
5. Checklist items not reported below were checked and found clean (see "Checked, no issue").

## Checked, no issue
- **Cross-org IDOR (buyer, processor, FPO admin):** every action takes `orgId`/`userId` from `requireSession(role, { action: true })` and never from the form; lookups filter by both id and org in SQL (`buyerAgreement`, `fpoAgreement`, `heldBatch`/`everReceived`, `getBuyerBatch` latest-custody filter, `received()` for processors); another org's id is `not_found` → 404. Tests green: `actions.int.test.ts:118-129` (buyer and admin), `processor/actions.int.test.ts:95`, `processing/actions.int.test.ts:111,160`.
- **Role checks:** every page/layout/action under `(buyer)` and `(processor)` guards itself; `tests/guard-coverage.test.ts` walks `src/app` with the TS compiler and fails on a missing or wrong-role guard (green, 9/9). `src/proxy.ts` redirects `/processor` too but is not the boundary.
- **Batch and attestation reads for buyers:** producer IDs only (EV16), scoped by latest custody to the buyer org; `batchAttestations` restricts to plots of the batch's own org.
- **Amount and quantity validation:** isomorphic parsers (`format.ts:parseAmount/parseKg`, `processing/validate.ts:parseKg`) with explicit regexes, digit caps and ranges (≤ ₹10 crore, ≤ 1,00,000.0 kg, ≤ 99,999.9 kg), re-checked server side; the grade is one of five literal values (`grades.ts`), DB CHECKs mirror it (`agreements_grade_check`, `settlements_grade_check`, `agreements_amount_check`, `processing_steps_kg_check`); the contract rejects zero terms, `minGrade > 100`, past deadlines; `kgToGrams` is exact integer arithmetic. `ensureBuyer` mints whatever a buyer needs — mock INR by design (not real money), noted only.
- **Idempotency / replay:** fund and refund recover a concurrent duplicate from its chain event (`idempotentStep`); settle recovers a lost release from `Settled` logs, de-duplicates by `txHash`, and `judgedBefore` stops identical `not_released` judgements from being re-anchored (CR-203); one release per batch across agreements is held by `batchReleased` on chain and the partial unique index 0031; grades are single-use (`quality_attestations_no_replace`); processing steps are unique per (batch, processor) by index and app check; hand-on twice → `not_held`.
- **Solidity:** checks-effects-interactions in `fund`/`refund`/`settle` (status and `batchReleased` set before the token transfer; token is the operator-minted MockINR), operator-only `createAgreement`/`settle`/`mint`, buyer-only `fund`/`refund`, disjoint deadline windows (`settle` ≤ deadline < `refund`), EIP-712 domain with `block.chainid` and `address(this)`, low-s and v∈{27,28} enforced before `ecrecover`, zero-address checks, 0.8 checked arithmetic, `BatchRegistry` strictly in-order append with no overwrite; events emitted on every state change. `forge test` is part of `contracts.yml`.
- **EVM key handling:** operator and per-org keys are generated through one routine (`crypto/key-file.ts`: `wx` temp + `link`, 0600/0700 tightened), never logged (addresses only), read from `DATA_DIR` through `runtimePath` (untraceable, EXE39); the deploy script hands the key to forge via the child environment (`UDGAM_DEPLOY_OPERATOR_KEY`), with a minimal env and no argv; Anvil dev keys are never used (`fundOperatorOnLocalAnvil` requires chain 31337 and an `anvil` client version); `orgKeyPath` validates `orgId` (`^[A-Za-z0-9_-]{1,64}$`) so no path traversal; the viem client refuses a key that does not match the deployment's operator.
- **Anchor integrity:** strict seq order, adoption only when the on-chain hash equals the ledger hash, `failed` halts anchoring until an operator resolution (`resolve.ts`), the audit compares stored and recomputed hashes and reports holes; `last_error` is never exposed publicly (`evmFieldsFor` returns status only).
- **DB layer:** every raw `sql` template is parameterised; the only `sql.raw` (`closure.ts:16`) interpolates a closed `Field` union literal; triggers 0027/0030/0031/0032/0034 enforce the status machine, append-only rows, holder-only custody and processing, and the one-release-per-batch rule for any writer; migrations run forward-only at boot.
- **Scripts:** seed refuses outside explicit dev/test or E2E=1 (EXE35) and writes credentials 0600; `cloud-setup.sh` verifies SHA-256 for Foundry and solc and prints no env values; `check-bundle-secrets.sh` and `check-trace.mjs` name variables/paths only; `ledger-audit`/`ledger-evm-resolve` load no key.
- **Workflows:** least-privilege `permissions`, no `pull_request_target`, no untrusted interpolation, gitleaks pinned by SHA; e2e artifacts hold only throwaway data (per-run random `BETTER_AUTH_SECRET`, committed demo password).
- **next.config / .gitignore / deploy files:** security headers on every response, CSP per request in `src/proxy.ts`, `outputFileTracingExcludes` covers data, keys and env; `.secrets/`, `.env*`, `*.key`, `data/`, `contracts/{out,cache,broadcast}` ignored (SEC-201 for the gaps); no Dockerfile/compose in the repo yet (M-003). The 3 MB Server Action body limit applied before the guard (`next.config.ts:24-28`) is a known, accepted M-001 item for the uploads reviewer.
- **Error and log leakage:** `ChainError.reason` carries viem's `shortMessage` (no URL); unknown errors are rethrown to Next's generic boundary; the processor actions log `errFields` only.
- **Design notes, not vulnerabilities:** a processor may hand a batch to any buyer organisation (D9 trust model: the FPO still settles and the buyer still grades); the escrow's "delivered kg" is the batch's fresh-cherry `quantityKg` from `batch_created`, not the processor's output kg.

## Verdict
No Critical or High. **Low: 3 (SEC-200, SEC-201, SEC-202). Info: 2 (SEC-203, SEC-204).**
