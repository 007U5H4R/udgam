## Checklist — checked, no issue

- **authn/authz, role boundaries, IDOR, cross-org:** every `(admin)` page, layout, Server Action and route handler calls `requireSession('admin'…)` first and takes `orgId` from the session (`tests/guard-coverage.test.ts` enforces it; verified by reading each file). Services scope by `farmers.orgId` / `batches.orgId` / `user.orgId` joins (`review/queue.ts:81`, `review/detail.ts:82`, `review/rerun.ts:42`, `plots/plots.ts`, `plots/registration.ts`, `attestations/attach.ts:120–132, 263–283`, `enrolment/assign.ts:21–33`, `enrolment/codes.ts:37–63`, `enrolment/enrol.ts:131–137`, `custody/transfer.ts:41`, `batches/eligible.ts:36`). Probe: other org's plot → `plot_not_found`; other org's attestation download, wrong plot → 404 identical to unknown; agent → 403; signed out → 401 (route) / 307 to `/sign-in` (pages). The review-detail cross-org photo-reuse signal reveals only a boolean, never the other org's time (`detail.ts:128`).
- **Session, cookie, CSRF:** cookies `httpOnly`, `sameSite=lax`, `secure` in production (`auth.ts:98–101`); `role`/`orgId` are `input:false`; Server Actions rely on Next's origin check + lax cookies; the one cookie-authenticated route handler outside the proxy (attestation POST) checks `Sec-Fetch-Site` then `Origin` (`route.ts:33–43`): probe shows `cross-site`, `same-site`, foreign `Origin` and `Origin: null` all refused 403 `not_allowed`; only a request with neither header (non-browser client holding the cookie) is accepted, which is not CSRF.
- **Input validation / SQL injection:** zod on every admin input (`plots/actions.ts`, attestation route, `telemetry.ts`); the one `sql.raw` (`ledger/closure.ts:16`) interpolates a compile-time literal from a 4-member union; all other `sql` templates are constants or bound parameters. Probe: `batchId = "B-' OR 1=1 --"` → 404.
- **File upload / path traversal:** attestation POST checks the session, origin and declared Content-Length before reading the body, then `file.size`, PDF magic, issuer (control/format chars, banned wording, 120 chars), calendar dates; a Content-Length of 100 with an 11 MB body → 413 (`req.formData()` reads the whole body, but the cap is the route's own). Download hashes the bytes against the anchored `file_hash` and confines `file_path` to DATA_DIR: with the DB trigger dropped and `file_path` set to `../../../../etc/passwd` or `/etc/passwd` → 404; a readable file inside DATA_DIR with the wrong hash → 500 `file_changed` (never served). The served PDF carries `Content-Disposition: attachment`, `nosniff` and `CSP: sandbox; default-src 'none'`, so a PDF with `/OpenAction /JavaScript` (accepted by the magic check) never runs in-origin. Plot uploads: 2 MB cap, `<!DOCTYPE` refused before XML parsing (XXE/billion-laughs), ≤ 1000 vertices, India bounding box, no holes, `kinks` self-intersection check. Per-user signing-key path rejects `../../evil` (`signing-keys.ts:26–31`).
- **SSRF / external fetches:** provider URLs are constants (`GFW_BASE_URL`, `CDSE_TOKEN_URL`, `CDSE_STATS_URL`); no user input reaches a URL; 8 s per-call timeouts with AbortController; bodies validated. Only the redirect/credential point of SEC-100.
- **XSS:** the only `dangerouslySetInnerHTML` outside the embedded feed is the QR SVG (`BatchQr.tsx:18`) built by `qrcode` from a server-formed URL whose only variables are the anchored `B-…` id and the 12-hex short hash; the embedded feed escapes `<`, `>`, `&`, U+2028/9 as JSON `\u` escapes (`embed.ts`): an override reason `</script><img src=x onerror=alert(1)> …` and issuer `</script><b>…` are anchored, served and rendered as text only (probe: `embedHasScriptClose: false`, `embedHasLt: false`; certificate view shows the reason verbatim as text). SVG map labels are React-escaped. OG/metadata: `ogVariant('<script>', …)` → neutral image; title/description built from a fixed district list and an enum crop label; Next escapes meta content. CSP on the real server: `script-src 'self' 'nonce-…' 'strict-dynamic'`, `object-src 'none'`, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`; every `<script>` in `/verify` carries the nonce or is the `application/json` data block; tile host only on `/admin*` documents.
- **Enumeration / h handling:** batch ids are `B-` + 8 random Crockford chars (40 bits) and `h` is 12 hex (48 bits) compared with `timingSafeEqual`; missing, empty, wrong, upper-cased, over-long `h`, unknown batch all answer the identical 404 on the API (`{"error":"not_found"}`, same headers) and the same generic metadata on the page; the HTML 404 for an unknown batch and for a wrong `h` have the same size. OPTIONS → 204 `allow: GET, HEAD, OPTIONS`; no CORS headers (a foreign `Origin` gets no `access-control-allow-origin`).
- **Caching:** feed, GeoJSON, health, telemetry, attestation answers `no-store`; `/verify` HTML `private, no-cache, no-store, max-age=0, must-revalidate`; the public key `public, max-age=300` (acceptable for a public key); OG PNG `public, max-age=0` (static). GeoJSON `content-type: application/geo+json`, `content-disposition: attachment; filename="udgam-B-…-eudr.geojson"` (anchored id only).
- **Public data exposure:** beyond SEC-101, the EUDR file carries `ProducerName` = `PR-…` producer id, `ProductionPlace` = district + state, 6-dp coordinates, Point under 4 ha; no names/identifiers/phones (probe sentinels absent in feed, GeoJSON and HTML). `/.well-known/udgam-ledger-key` publishes only `{kty,crv,x,y,kid,use,alg}` (no `d`). `/api/health` reveals version, short commit, `lastSeq`, checkpoint age, key presence and provider state (unauthenticated; intended by §15, nothing secret).
- **Rate limits / replay:** `/api/telemetry` is bounded (411 without Content-Length, 413 > 512 B, 30/10 min per client address, closed event set). `/api/verify` has no limiter; the work per request is a few indexed queries and ≤ 100-leaf Merkle trees, and the only write it can cause (an on-demand checkpoint, `feed.ts:124`) is idempotent and needs a valid link. The client address is the **last** `X-Forwarded-For` hop (`client-ip.ts`), correct only behind a proxy that overwrites the header; that deployment assumption is already tracked (EXE14, TSK-27.3, PRE-4) and is out of this area.
- **Ledger integrity, keys, tamper detection:** `ledger_entries` and `ledger_checkpoints` are append-only by trigger (probe: UPDATE → `SQLITE_CONSTRAINT_TRIGGER "ledger is append-only"`); `append` runs under `BEGIN IMMEDIATE` with `seq` as PK; checkpoints sign `jcs({v:1,id,fromSeq,toSeq,merkleRoot,prevCheckpointHash,ts})` with the P-256 ledger key (0600 file in a 0700 dir, atomic create, modes tightened on load, private member never returned/logged); the published key is the only trust anchor and the verifier checks `kid` = RFC 7638 thumbprint of the supplied key (`proof.ts:151–163`), so a feed cannot smuggle its own key; signed kinds verify `{kid,publicJwk,signature}` against `payloadStatement`; `__proto__`/`constructor`/`prototype` are refused at `format`. Probe with the trigger dropped: edited payload → `verifyChain` `{ok:false, seq:6, reason:'payload-hash'}`, feed still served but the browser verifier fails at `payload-hash`; with payload, `payload_hash` and `entry_hash` recomputed → the server refuses the feed (`feed: ledger entries no longer match checkpoint 1` → 503), and the next entry's `prev_hash` would fail `verifyChain`. Health reports `keyMismatch` (503) when any checkpoint's `kid` is unpublished. The Merkle construction matches RFC 6962 (bottom-up pairing with odd carry-up is the same tree as the recursive split; inclusion check is RFC 9162 §2.1.3.2). Known design limits, not findings: the server does not re-verify the chain before serving (TP16: the visitor's browser does; `pnpm ledger:audit` exists), and a signed payload proves which server-held key signed, not who (TP15 wording).
- **Error and log leakage:** route handlers log `errFields(err)` (class only) and answer `{"error":"unavailable"}`; provider clients log status/class, never the key or token; `env` proxy is non-enumerable and `toJSON` returns names only; the attestation download logs ids only.
- **Insecure defaults / env:** `BETTER_AUTH_SECRET` required in production; fixture provider refused in production unless `E2E=1`; `DEMO_MODE` alone cannot enable the demo in production (`demoEnabled` with `NODE_ENV=production`, no `E2E` → `false`; `?__tamper=`, `?state=` → ignored); `E2E=1` on a real deployment would expose the test surfaces (documented, EXE12/EXE33). The demo page is inert in production; when on, it signs in as the seeded agent server-side with its own cookie and signs out again; the plaintext `seed-credentials.txt` exists only in dev/e2e data directories.
- **Privilege escalation via enrolment/invite:** `issueCode` requires the agent and the admin to be in the session's org; codes are hashed; revocation is org-scoped (`enrol.ts:131–137`); not re-reviewed beyond the admin side (enrolment belongs to the capture area).
- **Dependency risk:** no new runtime dependency in this area beyond those CI audits (`@tmcw/togeojson`, `@xmldom/xmldom`, `qrcode`, `@turf/turf` pinned).
